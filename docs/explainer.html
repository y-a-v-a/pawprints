Technical notes · Pawprints for macOS

Inside Pawprints

Pawprints is a cosy detective game for the Mac. Each case is generated from a seed, the suspects speak through Apple's on-device language model, and every picture is painted on the Mac by Image Playground. Nothing goes over the network. This page explains how it is built, and which measurements shaped it.

Written by Claude, who built Pawprints in a single Claude Code session on 22 October 2026, for Vincent Bruijn. The code is at github.com/y-a-v-a/pawprints.

A three-billion-parameter model is a lovely voice actor and a poor game master.

Left alone, the on-device model repeats itself, forgets its alibi and makes up testimony. Given a line to say and a mood to say it in, it is quick, funny and nearly always right. So Pawprints splits the work. A deterministic engine decides every fact. The model only decides how each fact sounds.

Before any game code

Measure the model, then design around it

The brief was open: suggest five apps to build on apfel or Apple's Foundation Models, argue about which is coolest, and build it. Before writing game code, I asked a subagent to rank the five ideas and to test every risky assumption against the real model with apfel, the command-line front end to the same on-device model. A detective game where you question suspects in your own words won the ranking. The same probes showed that the obvious way to build it would fail.

Four results decided the architecture.

Decision: the engine writes every fact as a plain first-person line, the script. The model only restyles the script in the character's voice, and code checks the result before anyone sees it. If nothing passes, the suspect says the script word for word.

Decision: a cosy theft. Violent or rude questions get an in-character deflection from the engine, and a guardrail error, when it does happen, gets the same treatment instead of an error message.

Probe 3

Replaying the conversation made it copy itself

With the transcript sent back every turn, one suspect said Edmund was an old friend, and we had no quarrel. three turns running. A composure score set by the model jumped from 10 to 0 in one step, and the suspect never confessed even after both pieces of evidence were shown.

Decision: every line is a fresh session holding three things: the persona, the director's note and the question. Composure and confessions live in the engine.

Probe 4

Free text has no stop condition

Without a schema the model wrote both sides of the scene, took 28 s per reply and confessed in its first turn, inside a script it had invented. With a one-field JSON schema it took 1.5 to 2.7 s. But about 1 turn in 8 never closed its string and ran on for up to 60 s. A token cap turned that into broken JSON a quarter of the time.

Decision: guided generation for every reply, streamed, and cut by the app once it has enough sentences.

Architecture

The engine directs, the model acts

The code is one Swift package with five targets. MysteryKit holds everything that matters and has no UI: the case generator, the engine, the wrapper around the language model, and the queue of pictures to paint. The SwiftUI app, a headless command-line harness and a small painting helper sit on top of it. The tests run against MysteryKit alone, so they need neither a window nor the model.

Cases

A case is a seed

CaseGenerator.make(seed:) builds a whole mystery from one 64-bit number using a SplitMix64 generator, so the same seed always gives the same case, and players can trade "case 4127". It picks a setting (5), a stolen heirloom, four suspects from a cast of 14 animals, a motive (5), an embarrassing secret (5), a hiding place, and one of three plots. Then it writes the text of every notebook card the player could ever find. The model never writes a card.

Casting has one hard rule. The trace left at the scene (a feather, grey fur, flour on the handle, an inky smudge…) must fit exactly two suspects: the thief and the red herring. The generator searches the shuffled cast for a pair that shares a trace while the other two don't. A test checks the rule on 400 seeds.

Every suspect has a role. The thief lies about where they were. The red herring lies too, to hide something embarrassing. The witness and the loner tell the truth, and between them they hold the clue that breaks the thief's story.

The route to the answer is a short chain of deductions, and the plot decides how its last link breaks. Each case uses one of three plots, so the same cast can't be solved the same way twice. Two of the notebook's cards are written by the notebook itself: once both halves of a contradiction are in it, the engine adds the deduction automatically.

Dialogue

One reply, from question to notebook

Every turn takes the same path. The engine answers the question in plain words and returns a Directive. The Voice actor asks the model to say it in character, checks what comes back, and tries again if it has to. Exhibit 7 is a real turn, recorded this morning by replaying case 15 with PAWPRINTS_DEBUG=1. I chose it because almost everything went wrong in it.

Guided generation as the stop condition

Every reply is a one-field @Generable struct. The schema is what stops the model writing both sides of the scene. Streaming it lets the app stop early: Voice watches the snapshots and cancels once the line has enough sentences (one more than the script has, and at least three), runs past 20 words per sentence, gets stuck, or hits a 12-second deadline.

Sources/MysteryKit/Voice.swift, rewrapped

@Generable
struct SpokenLine {
    @Guide(description: "Exactly what the character says out loud, …")
    var line: String
}

for try await snapshot in session.streamResponse(to: prompt,
        generating: SpokenLine.self, options: options) {
    line = snapshot.content.line ?? line
    if Self.sentenceCount(line) >= maxSentences
        || line.split(separator: " ").count > 20 * maxSentences
        || Self.isRunaway(line) || Date() > deadline {
        line = Self.completeSentences(line)  // keep finished sentences
        break
    }
}

Checks on every draft

A draft is rejected and retried if it repeats an earlier line too closely, leaves out a name or a word the directive requires, or fails the grounding filter. The filter drops any sentence that names a suspect, a room, the owner or the stolen item that the script and note never mentioned. On the third attempt it trims the draft instead of rejecting it. If the facts still aren't there, the script is used as written.

The filter is strict on purpose. In the last play-test, a crow who was innocent of the theft was shown that he had been seen slipping away, and replied I don't think you could possibly have missed me leaving the kitchen with the Thornbury Tiara. That one sentence would have sent a player after the wrong suspect. Now it never reaches the screen, at the cost of an occasional extra second, as in Exhibit 7.

Drift the checks don't catch is harmless by design. In the same replay the fox moved the time of the crow's disappearance from just before it all began to just before the show concluded. The notebook card, written by the engine, still says the right thing, and the notebook is what the player reasons from.

Understanding what the player types

Free text first goes through cheap whole-word rules. Texting shorthand is expanded (did u see anybody becomes did you see anybody), you took it is an accusation, and a skilled cook is not violence. Only what the rules can't place goes to the model, as a classifier that must answer with one of ten topics.

@Generable
struct QuestionTopic {
    @Guide(description: "What the detective is asking about", .anyOf([
        "whereabouts", "saw_anything", "about_another_person",
        "about_a_place", "about_the_owner", "about_the_stolen_item",
        "about_yourself", "accusation", "small_talk", "violence",
    ]))
    var topic: String
}

Naming a piece of evidence (why was there a feather?) or throwing a known fact at someone (Dr. Ashby saw you slip away) counts as showing them that card, so typing and clicking lead to the same places.

Stage directions belong to the engine

The first version let the model pick a gesture from a list. In the second play-test, smiles warmly was 49 of 97 gestures, including during confessions, because it was first in the list. Now the engine picks from the mood: a rattled suspect goes quite pale, a flustered one fidgets, and a nervous bird ruffles a few feathers. Every third line or so gets one of the character's own openers, such as the badger's Harrumph!

Found while writing this page

To collect real traces for this page I replayed two cases, and they turned up four problems, now fixed. Accused in case 7, the owl's answer came out as I-I-I-I-I-I-I-… for 12 seconds. The stammer never finished a word, so neither the sentence cut nor the word cut fired, and the junk passed every check. A reply with a "word" over 30 characters, or one word making up more than half of it, now counts as stuck: the stream stops and the next attempt runs. The same accusation now takes 1.8 s.

The other three were smaller. The thief's confession in the finale read My dear Inspector, Very well, Inspector, I confess, because Very well wasn't known as an opener. The persona told the actor You is the Reverend's distant cousin. And the build had a leftover warning. There are tests for the first and third.

Pictures

Painting the case on the Mac

Image Playground's ImageCreator paints every picture in the game: the title art, each case's cover, the owner, the stolen item, the cast, the rooms and the evidence. A case needs about a dozen paintings at roughly 2.6 seconds each. They are scaled from 1,536 to 768 pixels, saved as JPEG and cached per case, so a case is only ever painted once. Every prompt has a plainer fallback, tried if the first is refused.

Image Playground does not paint people, and it refuses any prompt that it thinks might depict one, with the error conceptsRequirePersonIdentity. That is the main reason the cast are animals. Even then, the words matter more than the subject. A --paint-all launch flag paints every prompt in the content tables and logs each refusal, and it took three passes to get them all accepted.

Image Playground also only paints for an app with something visible on screen. From a command-line tool it throws backgroundCreationForbidden, which is why swift run isn't enough and the build script assembles a real, signed app bundle.

The bug that shaped the bundle

When the game was open, apfel stopped working

At 21:34 I launched the game so the subagent could play-test it blind. Its play-test came back with every line marked [fallback]: from that minute, every model call it made from the command line had failed with GenerationError error -1, plain apfel included.

The game wasn't doing anything wrong. Once a process has used ImageCreator, macOS keeps Image Playground's extension, GPNonUIExtension, alive for that process's whole lifetime. While it lives, command-line clients of the language model fail with error -1, and apps with a window still work. Releasing the ImageCreator doesn't help; quitting the process frees the model at once. A 40-line test app reproduces it on macOS 26.5.2. For someone who uses apfel every day, a game that silently breaks it for as long as the game is open isn't acceptable.

The details that make the helper work:

  • The queue is just files. Each PaintJob is a JSON file in ~/Library/Caches/Pawprints/queue/, written to a hidden temporary name and then renamed, so the helper never reads half a job. Urgent jobs, such as the room you just walked into, get a 0- prefix and sort first.
  • It is launched quietly. The helper is an LSUIElement app inside the game's bundle, opened with activates = false, so it never takes focus or shows up in the Dock. Only one runs at a time.
  • It has to show something. Image Playground only paints for a process with something on screen, so the helper shows a transparent 2 × 2-point panel that ignores the mouse.
  • It leaves notes. A refused prompt leaves a .failed file beside the output, so the game stops waiting and keeps its placeholder.

Build and test

No Xcode project, three kinds of test

Everything builds with SwiftPM from the command line. scripts/build-app.sh builds the game and the helper in release mode, then assembles the bundle by hand: it copies the binaries, writes both Info.plist files, turns the icon into an .icns with iconutil, and signs both apps ad hoc.

└── Helpers/
    └── Pawprints Painter.app/Contents/
        ├── Info.plist        LSUIElement = true
        └── MacOS/PawprintsPainter

Testing a game that talks happens at three levels.

  • Unit tests (swift test, 26 tests, under a tenth of a second). 400 seeds produce well-formed cases. The trace always fits exactly the thief and the red herring. All three plots occur, and 150 seeds are solved by the intended route. Every answer has a script to fall back on, wrong accusations cost a star, the free-text rules behave, and a game survives a save and load.
  • The real model, headless. pawprints-cli play 15 plays a whole case against the on-device model and prints every line with its timing; it took 19 seconds this morning. pawprints-cli repl lets you play in the terminal, and PAWPRINTS_DEBUG=1 prints every rejected draft, which is where Exhibit 7 came from.
  • The real interface. --autoplay plays the intended route through the actual UI, and screenshots are taken by window ID. Two blind play-tests by the subagent did the rest. The first ran into the error -1 bug, and noticed that two different cases were solved with exactly the same steps, which led to three plots instead of one. The second played five cases without spoilers: all were fair and solvable, the median reply took 1.3 s, and it found the smiles warmly problem and the crow's invented tiara.

For the next person

What I'd tell anyone building on Foundation Models

  1. Probe with apfel before you design. A few dozen command-line calls answered the questions that decided this architecture. Remember < /dev/null: apfel waits forever on an open, non-terminal stdin.
  2. Give the model lines, not facts. Restyling a script keeps names and places. Revealing a fact loses them.
  3. Make every turn stateless. History makes a small model copy itself.
  4. Use @Generable as the stop condition, stream it, and cut it yourself. Neither prompts nor token caps stop a runaway string.
  5. Check every draft in code, and keep a fallback that is always right. The model may then be as playful as it likes.
  6. Keep the record of truth out of the model's hands. Here that is the notebook; in your app it might be a database row or a calendar entry.
  7. Expect Image Playground to refuse words, not just pictures. Lady, vicar, lord, diva, dealer, band, even holly. Test-paint every prompt and keep a plainer fallback.
  8. Don't hold an ImageCreator in a long-running process if anyone on that Mac uses the model from the command line. Paint in a helper that quits.
